# 调度耗时复盘（本地机制验证）

保留原 20 任务、双租户、4 个 Worker 槽位、每租户最多 2 个租约与 45 秒断言。真实 PostgreSQL、本地对象存储、fixture 模型和 AST 验收；没有调用真实模型或 Docker。共享 Windows 主机（8 个逻辑 CPU），未人为停止用户应用。报告不能当作生产并发容量证明。

## 定位与改动

采集入口：`.venv/Scripts/python.exe scripts/profile-scheduler.py --output benchmarks/reports/<新报告>.json`。保存实现摘要、逐任务事件时间线、操作原始样本和 P50/P95。SQL 只保存分类耗时，不保存参数、正文或连接信息。数据库不可用时提前退出，避免连接等待混入调度结果。

基线中验收收尾平均约 2.6 秒，AST 验收平均不足 2 毫秒。后续测量分离出 Git 补丁生成与应用是收尾的主要耗时；tokenization 与 advisory-lock 操作的总时长不足以单独解释超时。不根据 CPU 使用率推断根因。

1. 领取任务已经重建、校验的投影复用于同事务的租约事件，仍每次校验重建，且缓存深拷贝避免可变状态污染。
2. 仅工具执行量子恢复工具工作区。模型决策、结果消费及 fixture 验收不再重复读取、落盘整个工作区。
3. 运行中的量子等待不再附带全局空队列睡眠；空领取采用每租户 100ms 退避，保留租户公平份额、总槽位和数据库租约上限。
4. 两棵完整文件树一次 `git fast-import`，复用一个一次性仓库：生成实际补丁，重置原始树，`git apply --check`、实际应用、索引应用，再比较完整文件语义。典型 fixture 从 14 次 Git 启动减至 8 次。不跳过交付验证。

## 结果与复现边界

原始数据见 `benchmarks/reports/scheduler-*-2026-10-10.json`。`call_seconds` 包含测试内部创建任务；45 秒断言只覆盖创建后的调度。任务 P50/P95 从任务创建到最后持久事件，包含排队；每操作 P95 与任务 P95 不混用。嵌套跨度总时长不能相加。

旧版 `0a3aa1d` 第一次隔离运行 28.875 秒；第二次通过 `git archive 0a3aa1d` 提取原始源码，在相同数据库与对象目录再次运行。已保留此前评估中的 45 秒失败事实。本轮隔离基线通过，说明历史超时的全部条件尚未重现。

改动中间版本的 24.562、38.454、45.859 秒结果均保留；其中较慢结果不作收益证据。最终批量导入版本再次满足原断言，详细时长与分位见 `scheduler-after-final-2`、`scheduler-after-final-3`。样本和主机负载仍有限，不能用单轮速度宣称稳定提升比例或高并发能力已验证。

| 完整版本 | 测试调用总时长（含创建） | 原 45 秒调度断言 |
| --- | --- | --- |
| 旧版 `0a3aa1d` 两轮 | 28.875 / 31.688 秒 | 两轮通过 |
| 最终版两轮 | 26.046 / 32.250 秒 | 两轮通过 |

最终 Runtime/恢复/公平调度回归 67 passed / 1 deselected（20 任务用例已按上述方式独立测量）；补丁、仓库与工具专项 37 passed / 1 skipped；Ruff 和全后端 ty 通过。

补丁与仓库回归覆盖空文件新增/删除、目录形态变化、CRLF、二进制、Unicode 路径、执行权限、受保护 attributes、SHA-256；本机安全链接用例依主机能力跳过。旧 epoch 被 fencing 拒绝、重放一致性及失败回退继续由 Runtime 回归约束。

## 仍需完成

固定空闲主机、多轮交错基线/新版、受控负载实验，进一步区分 PostgreSQL 服务端等待、事务提交与操作系统进程启动。当前 SQL 分类耗时包含执行和等待，未独立测定锁等待；事件边界到下一次领取的间隔也包含持久提交开销，不能称为纯排队时间。真实模型、Linux/gVisor 与 S3 故障联调仍待环境。
