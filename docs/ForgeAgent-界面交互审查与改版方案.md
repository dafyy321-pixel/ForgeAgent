# ForgeAgent 界面、交互与运行逻辑改版方案

审查日期：2026-09-22。范围：保留的 Twitter 风格前端及项目既有架构方案。

后续实施状态：用户确认的 24 项建议已经落实到前端，详见 [24 项改版落地与验收](ForgeAgent-24项界面改版验收.md)。下文保留最初 30 条审查建议及依据，其中超出用户确认范围的扩展方向仍是建议；没有新增后端。

## 1. 结论与依据

目前界面主要按社交动态组织，而 ForgeAgent 的核心对象是有目标、约束、动作、检查点和验证凭证的长时任务。用户应当首先看到：正在执行什么、哪里需要自己介入、下一步能做什么、最终交付有什么依据。

建议保留白底、蓝色强调、左侧导航、中央连续内容和轻量分隔线；重新设计三栏的职责、任务卡片、详情工作区和状态反馈。三栏布局值得保留，但信息流应成为任务事件的阅读方式。

审查依据来自当前项目文件，不把演示数据当成真实执行结果：

| 当前证据 | 暴露的问题 |
| --- | --- |
| `src/variants/twitter/index.tsx` 中 `app.runs.map` 生成帖子 | 每条内容代表任务快照，没有真正的事件流语义 |
| 同文件 `index===0` 决定主视觉流程卡 | 排序位置影响表达，首条任务即使已完成仍可能展示固定的执行图 |
| 同文件机器人头像、认证标记、`@RUN` 和帖子操作栏 | 社交身份占据任务名称、状态和行动的视觉位置 |
| `style.css` 中大量 8–11px 文本，以及更小的移动端标签 | 信息虽然放进了屏幕，阅读和触摸仍然困难 |
| `tw-wide` 切换布局，右栏只出现在工作台 | 工作台到内页宽度跳变，辅助信息没有稳定的位置 |
| `src/Overlays.tsx` 的任务详情全部装入弹窗 | 长时阅读、查看代码和比较证据的空间受限 |
| `src/Views.tsx` 的恢复演示直接展示检查通过 | 缺少失败检查、未知外部效果与不可恢复原因的界面表达 |
| `src/useWorkspace.ts` 中取消直接进入 CANCELLED | 演示省略了取消请求、停止派发和效果结算过程 |
| 任务详情上下文即时读取全局启用技能 | 展示的内容不是创建任务时锁定的配置快照 |
| 架构方案第 4、5、7、8、14、16 节 | 任务、动作、证据、授权与恢复是产品主要对象，应决定信息结构 |

## 2. 建议的信息架构

全局对象关系：工作空间 → 项目 → 任务 → 动作 / 观察 / 审批 / 检查点 / 产物 / 验证凭证。任务可关联子任务；技能和记忆是可版本化的执行输入。后端领域模块不需要与一级导航一一对应。

建议一级导航控制在六项：工作台、任务、待我处理、交付物、知识与能力、运行分析。工作空间与项目切换固定在左上，设置放在左下。

| 现有入口 | 建议位置 | 保留的能力 |
| --- | --- | --- |
| 工作动态 | 工作台 | 活跃任务、需要介入的事项、近期事件 |
| 任务运行 | 任务 | 列表、筛选、搜索、任务工作区 |
| 审批中心、恢复中心 | 待我处理；同时嵌入关联任务 | 审批、恢复检查、结果待确认、补充输入 |
| 产物与验证 | 交付物；同时嵌入关联任务 | 预览、diff、凭证、下载 |
| 上下文 | 任务工作区的检查面板 | 本任务输入材料、预算、压缩历史 |
| 技能库、项目记忆、工具与连接 | 知识与能力的二级导航 | 技能、记忆、工具配置与版本 |
| 评测实验、运行观测 | 运行分析的二级导航 | 评测、成本、耗时、轨迹与故障 |
| 工作空间设置 | 左下设置 | 默认预算、并发、通知与工作空间配置 |

### 页面布局草图

桌面基准为 1440px：两侧外边距各 24px，左栏 224px，栏间距 24px，右栏 304px，中央约 816px。任务工作区允许收起右栏以扩大 diff 和日志区域。

│ 工作台     │ 待处理 2    活跃 1    今日交付 3    │ 阻塞与预算提醒     │

│ 待我处理 2 │ 需要你决定                         │ 最近验证结果       │

│ 知识与能力 ├──────────────────────────────────┤                   │

## 3. 30 条具体修改建议

P0 表示影响主流程理解或状态准确性，应在改版中优先解决；P1 表示信息与交互质量；P2 表示在结构稳定后完善的体验。以下是同一套完整改版的优先顺序。

### A. 整体界面和视觉

**01 · P0：移除工作台宣传横幅。** 当前“让想法，自在发生”和装饰流程图挤占首屏。把这一位置交给需要处理的审批、运行中的任务和失败告警。新用户且没有任何任务时，才显示简短引导。验收：1440×900 首屏可看到至少一条待处理事项及一条活跃任务，无须先滚过宣传内容。

**02 · P0：重新定义三栏职责。** 左栏负责去哪儿，中央负责当前工作，右栏负责当前对象的辅助信息。不要继续用“正在发生”和“能力伙伴”模拟趋势榜和推荐关注。验收：从项目进入任务，右栏内容随上下文变化，但栏位保持稳定。

**03 · P0：把任务标题和状态放回视觉中心。** 删除头像优先、认证标记和账号样式的 RUN 编号。标题在第一行，状态与项目在第二行，任务 ID 放入次要元信息；Agent 名称仅在确实存在多个执行者时显示。验收：扫视一张卡片即可读出“什么任务、什么状态、为什么、下一步”。

**04 · P0：统一文字尺度。** 页面标题 24–28px，区块标题 18px，任务标题 16px，正文 14–15px，辅助信息 12–13px；代码 12–13px 并允许放大。手机正文保持至少 14px，不再靠 6–9px 标签塞进桌面卡片。验收：100% 缩放即可阅读关键状态，浏览器 200% 缩放仍能重排使用。

**05 · P1：减少卡片嵌套。** 当前一条帖子内部又有卡片、流程图、进度条和动作栏。普通任务使用平面行式布局，以细分隔线组织；审批、失败和选中项才使用浅色容器。验收：普通任务最多两层容器，边框不会比内容更抢眼。

**06 · P1：建立一致的色彩语义。** 蓝色表示选中与主要行动；绿色表示已验证完成；琥珀色表示等待用户；红色表示失败；灰色表示历史或禁用。状态同时带图标和文字。蓝色按钮可用较深的 `#1479C9`，浅蓝用于背景，最后按实际前景/背景测对比度。验收：普通文字达到 WCAG AA 4.5:1，大字和必要非文本边界按适用标准达到 3:1。

**07 · P1：固定间距和控件几何。** 使用 4/8px 间距体系；卡片内边距 16–20px，区块间距 24–32px。容器圆角 10–12px，按钮 8px，状态标签可圆角更大。减少所有按钮都像“发帖”的胶囊形态。验收：同一级元素共享高度、边距和圆角 token。

**08 · P1：统一页头，避免双标题。** 内页目前同时出现“项目记忆”页头和“让经验成为下一次的起点”大标题。保留明确的功能标题与一行解释，例如“项目记忆 / 仅已确认内容可用于后续任务”。验收：每页只有一个主要 h1，首屏操作区不会被两套标题压下去。

**09 · P1：信息密度可切换。** 任务列表提供标准与紧凑两档，并保存偏好。紧凑模式缩小垂直间距、隐藏长描述，不缩小关键字号。验收：同样屏幕下可增加任务可见数量，状态和下一步操作仍可读。

**10 · P1：让窄屏重排内容。** 右栏在不足以承载内容时变成“任务信息”抽屉；手机任务详情使用全屏页面，审批变为专门审查页，diff 用单栏。底部只保留工作台、任务、新建、待处理、更多。验收：390px 无页面横向溢出；关键触摸区域至少 44×44px，固定工具栏不遮挡最后一项内容。

### B. 页面结构和主流程

**11 · P0：缩减一级导航并按用户动作分组。** 把十二个技术/业务模块平铺，会让用户先学习架构才能使用。采用前述六项导航，专业功能仍可从二级页面和全局搜索进入。验收：审批、恢复和补充信息都能从“待我处理”到达，完整功能不被删除。

**12 · P0：显式工作空间与项目作用域。** 当前项目主要依赖 hashtag 和列表筛选。左上放项目选择器，页头展示作用域；创建任务自动带入当前项目。切换项目时显示任务和待办数量变化。验收：任一审批、记忆和任务都能明确知道属于哪个项目，搜索可区分本项目与全部项目。

**13 · P0：把任务列表与事件流分开。** 一张任务快照不能代表一条新动态。任务列表按任务聚合；工作台近期事件来自任务创建、工具完成、审批请求、验证失败等结构化事件。优先展示待处理，再展示活跃，最后展示完成。验收：同一任务的更新可以折叠聚合，不会用重复大卡片刷屏。

**14 · P0：用结构化任务入口替代发帖框。** 简洁输入仍可保留，但提交前应明确目标、项目、验收条件与修改范围；模型、预算和技能放到可展开的配置区。按钮写“创建任务”，提交后进入任务工作区。验收：表单错误出现在对应字段，提交期间不重复创建，返回后草稿仍在。

**15 · P0：任务详情升级为可寻址工作区。** 任务使用独立 URL，宽屏支持列表旁预览，深入处理可进入完整页面；弹窗只保留给短确认。浏览器后退回到原筛选和滚动位置。验收：刷新、复制地址、打开新标签均能定位任务；不存在或无权限的任务有明确结果，不静默回到首页。

**16 · P0：右栏以阻塞和下一步为先。** 在任务中依次显示“需要你做什么”“当前阶段与最近更新”“预算/耗时”“检查点与配置”。技能列表仅在用户检查配置时展开。验收：用户无需在多个页面寻找导致当前 Run 停止的原因。

**17 · P1：任务详情采用有内容类型的执行记录。** 用户目标、计划变更、工具操作、审批、失败和交付用不同条目组件，保持统一时间轴。工具输出默认显示摘要、结论和证据链接，展开后看原文。验收：时间线能准确说明发生过什么，不用固定演示模板假装每个任务都经历相同步骤。

**18 · P1：主操作随状态改变。** 活跃任务显示“打开执行记录 / 请求暂停”；等待审批显示“审查操作”；失败显示“诊断与恢复”；完成显示“查看交付”。收藏改为“关注任务”并放入次级菜单，分享放在任务头。验收：每条任务只有一个最突出主操作，不再并排摆五个社交式图标。

### C. 与运行时一致的状态和交互

**19 · P0：把生命周期、阶段、等待原因分开。** 页面分别显示“运行中 / 执行测试”“等待中 / 需要审批”“等待中 / 远程工具处理中”。数据层应补齐 QUEUED 和 CANCELLING 等架构已定义状态，WAITING 不能都翻译成审批。验收：每种状态都有明确原因、最近变化时间和适用操作。

**20 · P0：用里程碑和证据替代虚构百分比。** 当前进度和阶段映射是样例值。任务计划可重排，不能用步骤数直接声称完成 68%。优先显示“复现完成 → 修改中 → 待验证”，已知总量的测试才显示“18/19”。验收：无可靠分母时不展示百分比，重规划后仍能区分已发生的事实与未来计划。

**21 · P0：审批以具体变更为核心。** 审查页先展示目标仓库、分支、资源、diff、外部影响和有效期，技术 JSON 收入“授权详情”。提供批准、拒绝并说明、返回任务；参数或目标版本变化则标记授权失效。验收：用户可在不阅读底层协议 JSON 的情况下理解授权内容；审批提交过程中有禁用、错误和失效反馈。

**22 · P0：恢复前显示逐项检查和不确定性。** 检查点存在、工作区可恢复、版本兼容、权限有效、预算足够、外部效果已确认都应有结果。存在 UNKNOWN 动作时进入“结果待确认”，明确哪些操作不会重试。验收：不再始终显示绿色“检查通过”，缺少条件时说明阻塞和可行处置。

**23 · P0：取消是一个过程。** 用户确认后先显示“正在取消”，停止新动作，等待在途操作结算；有未知外部效果时继续显示需要处理的事项。文案说明取消不会撤销已发布的变更。验收：没有未结算效果后才显示“已取消”，取消中禁止再次继续运行。

**24 · P0：完成页以验收条件和产物版本为中心。** 上方是验收清单，其次是 diff、文件和验证凭证；明确通过、失败、未运行、不适用以及各自证据。生成了文件不等于任务完成。验收：完成状态可追溯到具体版本产物与验证器结果，过期凭证不能给新版产物挂绿色标记。

**25 · P1：上下文、技能和记忆绑定任务版本。** 任务工作区展示创建/恢复时锁定的配置快照，全局开关影响后续任务。上下文检查提供“为什么加入、来自哪里、占多少预算”，压缩前后可对照并打开原始观察。验收：改全局技能不会悄悄改写运行中任务详情所显示的输入。

**26 · P1：子任务显示委派关系和预算归属。** 将子任务放在父任务的执行树中，显示目标、状态、结果引用和预算占用；等待子任务时解释父任务为何等待。A2A 外部任务标明来源与同步时间。验收：子任务成本不重复计入，取消父任务时能看见仍待确认的外部子任务。

### D. 反馈、可信度和后续扩展

**27 · P1：实时更新不打断阅读。** 新事件用“有 3 条新事件”提示，用户决定跳转；位于底部且启用跟随时才自动滚动。显示“最后同步时间”和连接中断状态。审批或恢复失败要在相关对象上保留错误，toast 只做轻量反馈。验收：更新不会丢失展开项、选中文字或滚动位置。

**28 · P1：补齐空、错、忙、失效等状态。** 区分还没有任务、筛选无结果、请求失败、无权限、离线缓存、任务不存在。只读、禁用和等待都给出原因。保留键盘焦点、可访问名称与 reduced-motion；手机抽屉支持 Escape、焦点约束和关闭后回到触发点。验收：任何关键动作完成、失败或中断，都有用户能采取的下一步。

**29 · P1：演示模式也演示真实分支。** 在固定位置显示“本地演示”；提供成功交付、审批拒绝、测试失败、可恢复中断、效果待确认等场景。不要给所有“测试连接”“验证”“恢复”固定成功。验收：不依赖后端也能评审完整状态变化，任何样例指标均带演示标识。

**30 · P2：把运行分析和可访问链接做成有明确边界的能力。** 分析中指标可点击到对应任务，时间范围与分母可见；评测显示固定配置、样本量和失败原因。区分“复制此设备任务链接”和后续真实共享，真实共享需有访问权限。验收：图表不会与明细矛盾，自建任务链接在其他浏览器不存在时能给出清楚解释。

## 4. 推荐的任务卡片和状态展示

```text
修复认证模块的并发刷新问题                       [审查操作]
forge-api · RUN-0842 · 最近更新 12 秒前

[等待你处理] 即将向 feature/auth-refresh 发布代码补丁
影响：2 个文件，新增 34 行，删除 8 行
已完成：复现失败测试、修改代码；待完成：发布后验证

已用 $0.84 / 上限 $5.00                  打开任务 · 更多
```

实际影响摘要必须来自待审批操作与当前产物，不从任务标题推测。蓝色主按钮只出现在当前最重要的动作上；取消与拒绝放在审查界面的清楚位置，不与普通查看按钮混淆。

| 生命周期 / 原因 | 用户看见的状态 | 主要行动 |
| --- | --- | --- |
| QUEUED | 排队中，等待执行资源 | 查看排队原因 / 取消 |
| ACTIVE | 执行中，附当前阶段与更新时间 | 打开执行记录 / 请求暂停 |
| WAITING / APPROVAL | 等待你审查指定操作 | 审查操作 |
| WAITING / TOOL | 等待远程工具，显示最近回执 | 查看工具状态 |
| WAITING / CHILD_RUN | 等待子任务，显示子任务摘要 | 查看子任务 |
| WAITING / RETRY_TIMER | 等待重试，显示时间与原因 | 查看重试计划 |
| WAITING / RECONCILIATION | 外部操作结果待确认 | 查看对账或处置方案 |
| PAUSED | 已暂停，说明恢复条件 | 检查并继续 |
| CANCELLING | 正在取消，列出在途操作 | 查看停止进度 |
| FAILED | 执行失败，说明失败类型 | 诊断与恢复 |
| SUCCEEDED | 已验证完成 | 查看交付与凭证 |
| CANCELLED | 已取消，保留历史与已发生效果 | 查看记录 / 创建关联新任务 |

恢复能否进行、是否重新审批、失败后能否重试，由后端契约决定；前端不能仅根据一个按钮点击自行推断成功。

## 5. 落地顺序与验收方法

先处理 01、02、03、11–16，稳定导航、对象关系和工作区布局；随后处理 19–24，将生命周期、审批、恢复和交付语义统一；其余视觉规格与交互反馈在组件层一起落地。此顺序用于避免在错误结构上反复润色。

建议建立 `AppShell / TaskRow / TaskHeader / TaskWorkspace / EventItem / DecisionPanel / RecoveryChecklist / EvidenceViewer / Inspector` 组件。保留 React、TypeScript、Vite 与现有图标库即可完成 UI 改版；路由和状态模型应随上面的交互契约调整。暂不需要引入新的 Agent 框架来改善界面。

前端演示的数据至少区分 Task、Event、Action、Approval、Checkpoint、Artifact、Verification 和 RunConfigSnapshot。事件必须包含关联对象、发生时间和明确状态；不要在组件里根据列表索引编造执行阶段。真实接入时 UI 接收 Runtime 状态投影，而非成为业务状态的唯一事实源。

验收以任务场景为单位：创建并验证交付、拒绝审批后暂停、参数变化导致审批失效、工具超时且结果待确认、从有效检查点恢复、取消时存在在途动作、验证失败后修复、父子任务联动。每个场景检查桌面、手机、键盘、刷新和后退的连续性。

视觉验收建议覆盖 1440×900、1024×768、390×844；用真实长度中文、长文件名、多行失败原因与 200% 缩放检查。目标是首屏能判断待办与任务状态、一次点击到达相关处理页面、阅读日志时更新不抢滚动。这里列的是验收目标，尚未宣称已经实现。
